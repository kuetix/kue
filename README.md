# kue

The Kuetix CLI. It composes workflows into projects, talks to the
pkg.kuetix.com registry, and — because the full Kuetix standard library
(`std-core`, `std-cli`, `std-auth`, `std-http`, `std-ai`) is linked into the
binary — **runs workflows directly**.

## Running workflows

```bash
kue run ./flows/report.wsl arg1=value   # run a local .wsl / .swsl file
kue run acme/nightly-close              # download from the registry, verify
                                        # its SHA-256, cache it, then run
kue run .                               # auto-detected: build + run a project
kue run acme/nightly-close --check      # validate + report runnability only
kue run ./flows/report.wsl --json       # machine-readable result

kue run decision/cond.Number value=5 op=gt threshold=3 upper=10
                                        # run ONE linked-in transition directly,
                                        # no workflow file needed (see below)

kue modules                             # packages compiled into this binary
kue transitions --module std-http       # every action a workflow can call here
kue i acme/util-lib                     # cache a registry workflow for `kue run`
```

Aliases: `kue r` = `run`, `kue m` = `modules`, `kue t` = `transitions`,
`kue i` = `install`.

Registry workflows are fetched from `api.kuetix.com` (override with
`--host` or `KUE_HOST`), their content hash is verified against the server,
and they are cached under `~/.kue/cache/workflows/`. Before executing, `kue`
parses the workflow through the engine and checks that every action it calls
is provided by one of the linked-in packages (`kue modules`); a missing
module aborts the run unless `--force` is given.

### Running a single transition

A target shaped `<ns>/<class>.<Method>` — the same string `kue transitions`
prints for every linked-in action — runs that one action directly instead of
a workflow:

```bash
kue transitions --module decision              # see the signature first
#   decision/cond.Number(value float64, op string, threshold float64, upper float64)

kue run decision/cond.Number value=5 op=gt threshold=3 upper=10
# OK (2ms) [200]
# { "match": true, "op": "gt", "threshold": 3, "value": 5 }

kue run --check auth/password.HashPassword password=x min=8
# Transition: auth/password.HashPassword
#   ...
# Runnable: yes — linked into this kue build.
```

kue wraps the resolved action in a generated one-state workflow and runs
that; the trailing `key=value` pairs become the action's named arguments.
Values are typed on the way in: bare integers, floats, booleans and `[..]` /
`{..}` literals are parsed as their real type, everything else becomes a
string. `--check` reports the signature and whether the action is actually
registered (compiled in isn't the same as runnable — see `kue modules`)
without executing it; `--json` / `--force` work the same as for a workflow
target.

## Getting Started

### Quick Start with Runner Script

The application includes a `runner.sh` script for easy development:

```bash
# Run a workflow
./runner.sh run workflows/common/example.wsl

# Test all workflows
./runner.sh test

# Validate workflows
./runner.sh validate

# Build the application
./runner.sh build

# Clean generated files
./runner.sh clean
```

### Manual Build

```bash
make build-cli    # Build CLI application
make build-api    # Build API server
make build-consumer  # Build AMQP consumer
make build-service   # Build background service
```

### Run

#### CLI
```bash
./runtime/bin/kue-cli --workflow workflows/common/example.wsl
```

#### API
```bash
./runtime/bin/kue-api --port 8080
```

#### Consumer
```bash
./runtime/bin/kue-consumer --amqp amqp://guest:guest@localhost:5672/ --queue kue-queue --workflow workflows/common/example.wsl
```

#### Service
```bash
./runtime/bin/kue-service --workflow workflows/common/example.wsl --interval 60s
```

### Test

```bash
./runner.sh test
# or manually:
kue test
```

## Project Structure

- **cmd/** - Application entrypoints (cli, api, consumer, service)
- **workflows/** - Workflow definitions
- **modules/** - Custom modules
- **runtime/** - Configuration and logs
- **tests/** - Test files

## Shell completion

`kue completion <shell>` prints a completion script to stdout (bash and zsh):

```bash
# bash — current shell
source <(kue completion bash)
# bash — persistent
kue completion bash > /etc/bash_completion.d/kue

# zsh — drop onto $fpath, then restart the shell
kue completion zsh > "${fpath[1]}/_kue"
```

Run `kue completion` (no shell) for the full install instructions.

## Development

1. Add workflows to `workflows/` directory
2. Test: `./runner.sh test`
3. Validate: `./runner.sh validate`
4. Run: `./runner.sh run <workflow>`

## Notes

- Module cache (di.go, meta.go, modules.json) is automatically generated by kue run
- No need to manually run kueinit before running workflows
- The runner script handles all common development tasks

## Releases

Prebuilt binaries for linux/macOS/Windows (amd64 + arm64) are published to
[GitHub Releases](https://github.com/kuetix/kue/releases) on every `v*` tag:

```bash
curl -fsSL https://raw.githubusercontent.com/kuetix/kue/main/scripts/install.sh | sh
```

The bundled std packages (`modules/MODULES.md`, generated from
`modules/modules.yaml` — see [Project Structure](#project-structure)) are the
same for every platform build: ai, auth, cli, core, decision, http, jsondb,
mysql, push, redis, social-oauth.

To cut a release:

```bash
make tag TAG=v0.x.y      # annotated tag, refuses a dirty working tree
git push origin v0.x.y   # .github/workflows/release.yml builds + publishes
```

`release.yml` re-runs the CI gate against the tag commit, then runs
[GoReleaser](https://goreleaser.com) (`.goreleaser.yaml`) to build, archive,
checksum, and publish. Versions are immutable — cut a new tag rather than
force-pushing an existing one.

Before tagging, `make test-release` exercises the whole pipeline locally —
the generated module list is in sync, every platform/arch target
cross-compiles (`goreleaser build --snapshot`), and `scripts/install.sh`
installs a real build end-to-end (including its checksum-mismatch and
missing-version failure paths) against a local fake release server. CI runs
the same on every push (`release-pipeline` job in `ci.yml`) and again right
before a real tag publishes (`release.yml`).
